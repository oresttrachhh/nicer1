# Архітектура агента

Цей документ описує архітектуру автоматизованого агента, який працює з репозиторієм, які проблеми він вирішує, які навички (skills) використовує, які команди доступні користувачу, які дані передаються між етапами та як оркестратор обробляє помилки.

## 1. Які проблеми вирішує агент

- Автоматизація рутинних змін у репозиторії (створення/редагування файлів, оновлення документації).
- Пошук та аналіз коду (семантичний і лексичний пошук). 
- Підготовка чернеток PR/issue і взаємодія з GitHub (створення issue, отримання логів CI).
- Виконання діагностики — збирання логів, запуск перевірок (або запит на них) та підготовка описів проблем.
- Оркестрація багатоетапних операцій з контролем консистентності й відкатом у разі помилок.

## 2. Які skills (навички) використовує агент

Нижче перераховано логічні навички, які реалізуються через окремі модулі/інтеграції в системі: 

- Repository access (repo read/write): читання файлів, створення/оновлення файлів, створення гілок/комітів.
- Code search (лексичний): точковий пошук по символах/рядках.
- Code search (семантичний): інтелектуальне знаходження релевантних місць у коді за запитом.
- Issue management: створення та оновлення GitHub issues.
- File editing / push: створення або оновлення файлів у репозиторії.
- Actions & CI diagnostics: отримання логів workflow, аналіз результатів CI.
- Web / external search: пошук релевантної інформації в інтернеті (запити до пошукового API).
- Natural language understanding / intent parsing: перетворення запитів користувача у внутрішні дії.

(У реалізації кожна з цих навичок відображається у вигляді окремого інтеграційного адаптера, який викликає відповідні API.)

## 3. Команди, доступні користувачу

Приміри команд високого рівня (CLI/чат-інтерфейс):

- help — показати доступні команди і короткі описи.
- status — статус останньої операції / стан агента.
- search-code "<запит>" — провести семантичний/лексичний пошук у кодовій базі.
- edit-file <path> — запропонувати зміни у вказаному файлі (чернетка змін).
- create-file <path> <content> — створити файл у репозиторії.
- update-file <path> <content> — оновити файл (створити PR або прямий коміт залежно від політик).
- create-issue <title> <body> — створити GitHub issue.
- get-logs <workflow> [--job id] — отримати логи CI для діагностики.
- run-checks — запитати/ініціювати набір перевірок (CI) та зібрати результати.
- explain <path|code-snippet> — пояснити фрагмент коду або архітектурне рішення.

Кожна команда може бути реалізована як «planner» + виклики конкретних skills (адаптерів).

## 4. Дані, які передаються між етапами (pipeline)

Типова pipeline-структура і перелік даних:

1. User input
   - Сировинний текст запиту (рядок), метадані сесії, права користувача

2. Intent parsing / NLU
   - Розпізнаний інтеншн (наприклад: edit-file, create-issue), параметри команди, структури даних для виконання

3. Planner / Orchestrator
   - План дій (список кроків), порядок виконання, трансакційні контексти (id операції), таймаути, політики відкату

4. Skill dispatcher / Executor
   - Параметри для конкретних навичок: шляхи файлів, зміст файлу, запити для пошуку, фільтри
   - Час виконання, кореляційні id для логування

5. Skill responses
   - Результати інвокацій: успіх/помилка, полезні дані (новий blob SHA, URL PR/issue, лог-файл), діагностичні повідомлення

6. Aggregator / Response composer
   - Оброблені результати у вигляді, придатному для користувача: повідомлення, посилання на PR/issue, рекомендовані наступні кроки

7. Persistence / Audit
   - Логи операції, телеметрія, збережені чернетки, історія дій для відкату або повторного виконання

Формат даних
- Використовуються структуровані JSON-об'єкти між компонентами з полями: operation_id, step_index, component, timestamp, payload, status, error (якщо є).

## 5. Як оркестратор обробляє помилки

Принципи обробки помилок:

1. Валідація та раннє блокування
   - Перед викликом зовнішніх навичок оркестратор перевіряє параметри (права доступу, коректність шляху файлу, розмір вмісту тощо). Це дозволяє відсікати явні помилки ще до виконання зовнішніх операцій.

2. Таймаути і обмеження ресурсів
   - Для кожного виклику визначено максимальний таймаут; у разі перевищення операція припиняється і повертається помилка з діагностикою.

3. Повтори з backoff
   - Для помилок, що схильні до тимчасових збоїв (наприклад, мережеві), оркестратор здійснює кілька спроб з експоненціальним backoff.

4. Фолбек-стратегії
   - Якщо primary skill недоступний, оркестратор може переключитись на secondary adapter (наприклад, інша реалізація пошуку або кешовані результати).

5. Ідемпотентність і транзакційність
   - Дії, що змінюють стан репозиторію, оформлюються з operation_id і (де можливо) перевірками pre/post-condition. Якщо частина багатокрокової операції не вдалась — застосовуються компенсуючі кроки (rollback) або створюється чіткий звіт з інструкціями для ручного відкату.

6. Частковий успіх
   - Якщо операція складається з незалежних підзадач, оркестратор дозволяє успішно завершити ті підзадачі, що пройшли, і повернути детальний звіт про невдалі кроки з пропозиціями дій.

7. Ескалація і повідомлення користувачу
   - Коли автоматична обробка не може вирішити проблему, оркестратор формує зрозуміле повідомлення для користувача з детальною діагностикою, посиланнями на логи та рекомендаціями.

8. Логування і телеметрія
   - Всі помилки детально логуються з контекстом (operation_id, вхідні дані, відповіді від зовнішніх систем). Метрики використовуються для виявлення повторюваних проблем і налаштування threshold-ів.

9. Безпека при помилках
   - У повідомленнях про помилки не розкриваються чутливі дані; журнали з доступом до секретів зберігаються у захищеному сховищі.

## 6. Розширюваність

- Нові навички додаються як модулі/adapters, що реалізують єдиний інтерфейс (invoke(params) -> result).
- Planner може отримувати нові дії (commands) шляхом реєстрації handler'ів.
- Формат даних між компонентами (JSON) дозволяє швидко підключати зовнішні сервіси і тестувати fallback-поводження.

## 7. Приклади сценаріїв

1) "Оновити README"
   - Користувач: edit-file README.md
   - NLU -> intent: edit-file, path=README.md
   - Planner: отримати поточний вміст, застосувати зміну, створити коміт або PR
   - Executor: create_or_update_file -> повертає URL/sha
   - Response: "README оновлено" + посилання

2) "Діагностика упалу CI"
   - Користувач: get-logs workflow-name
   - Executor: get-actions-job-logs -> збір логів
   - Aggregator: аналіз log-лампочка (помилки, stacktrace) -> рекомендації
